# Why OuterTune 0.10.1 stops playing after 30 to 60 seconds

This is the bug InterTune exists to fix. Upstream's
[playback-errors megathread](https://github.com/OuterTune/OuterTune/issues/735) was closed as not
planned, so if you arrived from that thread, this is the whole answer.

## The symptom

Upstream OuterTune 0.10.1 stops playing partway through every track with:

```
Source error (2004): Response code: 403
```

Usually somewhere between 30 seconds and a minute in. It is not your account, your network or
your downloads. It happens on every YouTube Music track, at roughly the same point in each.

## The cause

In August 2026 YouTube began requiring a GVS proof-of-origin token from `ANDROID_VR` and `IOS`,
the two InnerTube clients upstream streams with. A client that owes a token and sends none is
granted a **cold-start allowance of roughly 1 MB** and then receives `403` for everything past
it.

The allowance is on **data, not time**. That is the part worth holding on to, because it is
what makes the symptom look inconsistent from one report to the next: the cutoff moves with
audio quality.

| Audio quality | Bitrate | ~Playback before 403 |
|---|---|---|
| High | 256 kbps | ~31 s |
| Default | 136 kbps | ~60 s |

Same allowance, different cutoff. Someone on High reports "about thirty seconds", someone on
Default reports "about a minute", and neither of them is misremembering.

## Why upstream's own check never caught it

Upstream lists `IOS` as its only fallback stream client. Worse, the resolution loop
deliberately skips `validateStatus` for whichever client is *last* in the list, and with a
single-element list `IOS` is always last. So its capped URL is handed to the player unchecked.

The check would not have caught it anyway. `validateStatus` sends a bare `HEAD` and accepts any
2xx, and these URLs are perfectly healthy at the head of the file. They only start returning
`403` past the allowance.

Upstream stopped active development in February 2026, which is why nobody upstream is looking at
this. Its playback-errors megathread was closed as not planned on 28 April 2026, four months
before YouTube began enforcing the token, so that closure was a wind-down rather than a decision
about this particular regression.

## The fix

Add the `VISIONOS` client (Apple Vision Pro, client ID 101), which is exempt from the token
requirement and needs no signature deobfuscation, and place it ahead of `IOS` in the fallback
list. `VISIONOS` does need a `visitorData` to clear YouTube's bot check, which the existing
`toContext` already supplies.

Measured on device, 22 August 2026, same track and same network:

| Client | Result |
|---|---|
| `VISIONOS` | full 6.13 MB track |
| `IOS` | **stopped at 1.05 MB, then `403`** |

The fix itself is 3 files and ~50 lines, and touches no UI. Downloads resolve through the same
code, so they are fixed too. Listening history is a neighbouring repair on the metadata path:
`ANDROID_VR` answers that call with `LOGIN_REQUIRED`, so history had been failing silently, and
`VISIONOS` returns a real `videostatsPlaybackUrl`.

It is deliberately a minimal diff against `v0.10.1` rather than a rebase onto a newer upstream.

## What it does not fix

The clients that will hand over a full track are ones InterTune can only use signed out, so
every request for the actual audio goes out anonymously even while you are signed in to the
app. Age restricted tracks, and anything only your own account can play, still fail. This was
already true of upstream's own stream clients and the fix does not change it. Only playback is
affected: library, playlists, likes and recommendations all use your account as normal.

## Expect this to break again

`VISIONOS` is exempt because YouTube hasn't gotten to it yet, not because it's blessed. yt-dlp
has had to re-pin its YouTube client versions repeatedly for the same reason. When this stops
working, the fix is likely a client version bump in
[`YouTubeClient.kt`](../innertube/src/main/java/com/zionhuang/innertube/models/YouTubeClient.kt)
rather than anything structural.

If playback starts returning `403` again, [open an
issue](https://github.com/ItzSkyeYT/InterTune/issues) and say which track and which audio
quality, because the byte count is what identifies it.

[AsterTune](https://github.com/yuuichi-s/AsterTune) reached the same conclusion independently.
