# #1190 — Searching "null" results in a crash

**What actually goes wrong (upstream):** `androidx.navigation`'s `NavType.StringType` treats
the literal path segment `"null"` as its null sentinel and decodes it back to an actual
Kotlin `null`, regardless of URL-encoding. Since the search route is built as
`"search/${it.urlEncode()}"`, searching the literal word "null" produces a route segment
that Navigation parses back into `null` rather than the string "null", crashing the app when
a non-nullable arg fails verification (or NPEs downstream).

**Where it lives in InterTune — already fixed:**
- `app/src/main/java/com/dd3boh/outertune/MainActivity.kt:730-733` — the `query` nav arg for
  route `search/{query}` is declared `nullable = true`, avoiding the verification crash.
- `app/src/main/java/com/dd3boh/outertune/viewmodels/OnlineSearchViewModel.kt:27` —
  `val query = savedStateHandle.get<String>("query") ?: "null"` recovers the intended literal
  "null" instead of using `!!`, avoiding a follow-on NPE.
- Both are already present with explanatory comments citing this exact upstream issue
  number. `LocalSearchViewModel.kt:27` confirms local (on-device) search never goes through
  navigation args at all (`MutableStateFlow("")`), so it was never exposed to this bug class
  either.

**Evidence:** Verified directly by reading the two files above (not just trusting a comment) —
confirmed the `nullable = true` declaration and the `?: "null"` elvis recovery are both
actually in place and internally consistent.

**Why not fixed this run:** Already fixed. Nothing to do.

**If still reported as reproducing:** Likely an old/cached APK build predating this fix, or a
different crash path not covered here (e.g. a different search entry point). Would need a
stack trace and exact app build/version from the reporter to investigate further.
