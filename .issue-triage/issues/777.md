# 777 — Crash when sharing artist from artist detail page [java.lang.IllegalArgumentException: invalid beforeContentPadding]

**Labels:** bug · **State:** scored · **Last scored:** 2026-09-02 · **Corroborated by:** #922

## What breaks
Opening an artist's detail page and tapping the top-right share icon kills the app with
`java.lang.IllegalArgumentException: invalid beforeContentPadding` thrown from Compose's
`LazyListMeasureKt.measureLazyList` — i.e. the artist screen's `LazyColumn` is measured with a
**negative top content padding** while the system share sheet is coming up.

## Where
`app/src/main/java/com/dd3boh/outertune/ui/screens/artist/ArtistScreen.kt:273-282`

```kotlin
LazyColumn(
    state = lazyListState,
    contentPadding = LocalPlayerAwareWindowInsets.current
        .add(
            WindowInsets(
                top = -WindowInsets.systemBars.asPaddingValues()
                    .calculateTopPadding() - AppBarHeight
            )
        )
        .asPaddingValues()
)
```

This is the **only** negative window-inset content padding in the whole app (verified by a
multiline grep for `WindowInsets(\s*top\s*=\s*-` over `app/src`). Every sibling screen — e.g.
`ui/screens/AlbumScreen.kt:180` — uses `LocalPlayerAwareWindowInsets.current.asPaddingValues()`
with no subtraction. The share button that triggers it is `ArtistScreen.kt:601` (`Intent.ACTION_SEND`)
/ `ArtistScreen.kt:610` (`Icons.Rounded.Share`). So the file is certain; the failing *branch* is not.

## Why the mechanism is NOT nailed (this is what caps the score)
The provider is `MainActivity.kt:526-545`:

```kotlin
val playerAwareWindowInsets = remember(bottomInset, playerBottomSheetState.isDismissed) {
    ...
    windowsInsets                                  // = WindowInsets.systemBarsIgnoringVisibility  (MainActivity.kt:459)
        .only(WindowInsetsSides.Horizontal + WindowInsetsSides.Top)
        .add(cutoutInsets.only(WindowInsetsSides.Horizontal))
        .add(WindowInsets(left = ..., top = AppBarHeight, bottom = bottom))
}
```

So the effective top padding is

```
top = systemBarsIgnoringVisibility.top + AppBarHeight − systemBars.top − AppBarHeight
    = systemBarsIgnoringVisibility.top − systemBars.top
```

which is **≥ 0 by definition** (the ignoring-visibility variant is never smaller than the
visibility-aware one). Worked through at the reporter's exact density from the logcat
(`density={2.625}`, status bar `mFrame=[0,0][1080,88]`):

- `systemBars.asPaddingValues().calculateTopPadding()` = 88 px → 33.5238 dp
- `WindowInsets(top = −33.5238.dp − 64.dp)`.roundToPx() = −256 px
- `AppBarHeight` 64.dp.roundToPx() = +168 px
- `systemBarsIgnoringVisibility.top` = +88 px
- **sum = 88 + 168 − 256 = 0 px exactly** — which is why it normally does *not* crash.

I could not establish what drives that sum below zero at share time. The logcat does show the
status bar flipping to `mVisible=false` and `MSG_WINDOW_FOCUS_CHANGED 0 0` right before the
`FATAL EXCEPTION`, so it is inset-dispatch-timing related — but the direction of that change
makes the sum *more* positive under the arithmetic above, not less. Candidate explanations I
could neither confirm nor rule out without a device: (a) a stale composition-time read of
`systemBars` racing a live `systemBarsIgnoringVisibility` during a forced subtree measure from
`dispatchDraw`; (b) `getInsetsIgnoringVisibility(statusBars())` returning 0 on One UI while the
visibility-aware value is still 88; (c) a ±1 px rounding residue at some other density.

## Evidence present / missing
- **Present:** full DEBUG logcat with the complete stack trace and the exact exception message
  (#777); numbered repro steps; a **second independent reporter** (#922) on a different version
  (0.10.0-b5 vs 0.9.3.1) with the identical exception and a screen recording.
- **Missing:** the `confirmed` label; any app class in the stack trace (it is 100 % Compose/
  framework frames); a maintainer repro; a device to run it on.

## Likely fix
Clamp the computed padding at zero, e.g. compute the top offset as a `Dp` and
`.coerceAtLeast(0.dp)` before handing it to `LazyColumn`, or drop the negative-inset trick and
draw the header behind the bar with a `Modifier.offset` instead.

## The single blocker
**Symptom vs root cause.** A `coerceAtLeast(0.dp)` clamp stops the crash but I cannot say *why*
the value goes negative, so I cannot say whether clamping silently breaks the intended
"header scrolls under the transparent app bar" layout on the devices where it currently works.
Phase 3 self-review would fail on "root cause vs symptom?".
