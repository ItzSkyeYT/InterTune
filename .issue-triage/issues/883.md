# #883 — Playing downloaded song from artist page fetches it online instead of locally

**What actually goes wrong (confirmed part):** `SongItem.toMediaMetadata()`
(`app/src/main/java/com/dd3boh/outertune/models/MediaMetadata.kt:166-185`, used when a song
comes from an online/YouTube API browse result, e.g. an artist page) never sets
`isLocal`/`localPath`, unlike `Song.toMediaMetadata()`
(`MediaMetadata.kt:123-164`, used for DB-backed library/downloads screens) which does.

The artist page (`ui/screens/artist/ArtistScreen.kt:383-460`, specifically the
`playerConnection.playQueue(ListQueue(... items = section.items.map { (it as
SongItem).toMediaMetadata() } ...))` call around lines 435-443) builds its queue from
`SongItem`, so even a song that's actually downloaded loses that fact once it's in the
queue.

Playback resolution — `app/src/main/java/com/dd3boh/outertune/playback/MusicService.kt`,
`createDataSourceFactory()` — resolves the "is this local" question by first checking
`queueBoard.getCurrentQueue()?.findSong(...)` (line 777); only if that returns `null` does it
fall back to a DB lookup (line 779). Since the artist-page queue supplies a non-null (but
local-info-blind) `MediaMetadata`, the DB fallback never runs, `song.localPath` is null
(line 782), and playback falls through to the online-fetch path.

**Where this leaves genuine uncertainty:** the `localPath` DB column is only populated for
"custom/external" downloads (`SongsDao.kt:287`, `registerDownloadSong`) — NOT for
"internal" (ExoPlayer-managed) downloads, which only set `dateDownload`
(`SongsDao.kt:283`, `updateDownloadStatus`) and are detected at playback time purely via
`downloadCache.isCached(mediaId, ...)` (`MusicService.kt:804-805`), a raw cache lookup by
ID that does NOT depend on the queue's `MediaMetadata` at all. The reporter says the bug
happens for **both** internal and external downloads, but the mechanism found here only
has a confirmed causal path for the external/custom-download case. For the "internal"
case to be explained the same way, the artist-page `SongItem`'s video ID would have to
differ from the ID under which the song was originally downloaded (an ID-normalization
issue elsewhere) — plausible, but not verified by static reading, and not something I could
confirm without a device or logs.
