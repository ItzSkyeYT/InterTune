# #965 — Authentication Tokens Stored in Plaintext

**What goes wrong:** YouTube session token (`innerTubeCookie`), `visitorData`, and
`dataSyncId` are stored unencrypted in the app's Jetpack Preferences DataStore.

**Where it lives:** Key definitions at
`app/src/main/java/com/dd3boh/outertune/constants/PreferenceKeys.kt:204-208`
(`VisitorDataKey`, `DataSyncIdKey`, `InnerTubeCookieKey`, plain `stringPreferencesKey`).
Backing store: `app/src/main/java/com/dd3boh/outertune/utils/DataStore.kt:24`
(`context.dataStore` — standard unencrypted Jetpack Preferences DataStore). Confirmed real:
no `EncryptedSharedPreferences`, `MasterKey`, `androidx.security`, or Keystore usage
anywhere in the app, and no crypto dependency in `gradle/libs.versions.toml` or
`app/build.gradle.kts`.

**Evidence:** Precise, verifiable claim (exact preference key names given), confirmed
directly by reading the source — not just trusting the report.

**What a fix would involve:** Either add `androidx.security-crypto` (a new dependency —
requires editing `gradle/libs.versions.toml`, forbidden) or implement Keystore-based
encryption by hand. The latter is technically SDK-only (no new dependency) but is NOT
confined to a small patch: ~10 files read/write these keys directly through the generic
`rememberPreference`/`dataStore[key]`/`dataStore.edit{}` API (`App.kt`, `ContextExt.kt`,
`LoginScreen.kt`, `SetupWizard.kt`, `AccountScreen.kt`, `AccountFrag.kt`, `SyncFrag.kt`,
`LibraryFrag.kt`, `ExperimentalSettings.kt`, `HistoryScreen.kt`), with no shared
token-specific accessor to intercept in one place. A real fix also needs a migration path
for existing plaintext values on upgrade.

**Why not fixed this run:** Blast radius exceeds the ≤4 files / ≤80 lines band regardless
of approach, and the clean approach needs a forbidden dependency change. Hard abort per
Phase 2 blast-radius rule.

**What would raise the score:** A maintainer decision to either accept the new dependency
(then it's a build-config change requiring explicit sign-off, not a routine triage fix) or
to introduce a shared token-accessor abstraction first (separate refactor PR) that a later
encryption patch could hook into cleanly.

**State:** blocked (needs a dependency/architecture decision beyond routine scope)
